# AGENTS.md

Constraints for AI agents working in this repo. Follow them unless the user explicitly overrides one in the current request.

## Read first

Before you change code, read:

1. [`docs/README.md`](docs/README.md): what the docs folder holds.
2. The rules file for the area you touch:
   - Routes, modules, folder placement: [`docs/rules/architecture.md`](docs/rules/architecture.md)
   - Server functions, transactions, validation: [`docs/rules/server.md`](docs/rules/server.md)
   - Pages, forms, tables, charts: [`docs/rules/client.md`](docs/rules/client.md)
   - Schema and migrations: [`docs/rules/database.md`](docs/rules/database.md)
   - Styling and theme tokens: [`docs/rules/styling.md`](docs/rules/styling.md)
   - Branches, checks, PR expectations: [`docs/rules/workflow.md`](docs/rules/workflow.md)
3. The product rule for the feature, if one exists in [`docs/product/`](docs/product/). Business behaviour comes from there, not from guessing at the code.
4. Any decision record that touches your change, in [`docs/decision/`](docs/decision/).

If a rule conflicts with the code, don't silently pick one. Report the conflict to the user.

## Code placement

- Pages go in `src/routes/`, written directly in the route file. Routes import from modules.
- Feature code goes in `src/modules/<feature>/`: `server.ts`, `types.ts`, `components/`. Create `hooks/` only when a hook is reused.
- Shared components go in `src/components/erp/`. The app shell goes in `src/components/layout/`.
- Never edit `src/components/ui/` by hand. It is generated by the shadcn CLI. Compose it from your own code instead.
- Never create barrel files (`index.ts` that re-exports). Import the defining file.
- Use the `@/` alias for imports from `src/`.

## Server and data

- Every server function validates its input. Use the helpers in `src/lib/validation.ts`.
- Writes that touch more than one row run in `db.transaction` with the synchronous `tx` API. Never `await` inside a transaction.
- Money is whole rupiah in integer columns. Dates are `YYYY-MM-DD` text.
- Schema changes: edit `src/db/schema.ts`, run `npm run db:generate -- --name short_name`, review the generated SQL, and commit it with the change.
- Never edit an applied migration in `drizzle/`. Add a new one.
- Never hand-edit `src/routeTree.gen.ts`. It regenerates on `npm run dev` or `npm run build`.

## Data safety

- Don't run `npm run db:seed -- --force` against any database except the local `data/app.db`. It wipes the ERP tables.
- Don't read, copy, or commit `data/*.db`, `.env*`, or anything under `/var/lib/erp/`.
- Never add secrets to committed files, including `infra/pm2/ecosystem.config.cjs`.

## Verification

Before saying a change is done, run and report:

- `npm run typecheck`
- `npm run build`
- For UI changes: `npm run dev` and open the affected pages. Check at least one wide and one short viewport.
- For server changes: call the function through the running app, or describe why you couldn't.

There is no automated test suite yet. Say so in your summary and say exactly what you checked. Don't claim something works if you didn't run it.

## Git and deploy

- Don't commit, push, or open a PR unless the user asks. Ask first when it's ambiguous.
- Branches: `main` is production, `staging` is staging. Don't push to either directly unless the user asks.
- Commit messages: short imperative subject, body explains why. Add the `Co-Authored-By` line the session requires.
- Don't run `infra/deploy.sh` or touch `infra/` servers unless the user asks. Deploys change live systems.

## Docs

- Change behaviour, change the doc in the same change:
  - Business rule changed: update the file in `docs/product/`.
  - New architectural choice: add a record in `docs/decision/` (next number, never reused).
  - New convention: update the matching file in `docs/rules/`.
- Don't rewrite an old decision. Add a new one that supersedes it and mark the old one `Superseded by`.
- Keep docs short and true. Point at file paths instead of pasting code that drifts.

## Scope

- Do what was asked. Don't refactor unrelated code, rename things for taste, or add features the user didn't request.
- When something is unclear and the choice matters, ask. When it's a small reversible choice, make it and say what you chose.
- Don't invent business rules. If `docs/product/` doesn't cover the case, ask or flag it as an open question.
